# KK Profiling migration notes

## Scope and privacy

The migration separates KK profiles from general portal records into restricted `kk_responses` records, keeps legacy workbook rows in private import staging tables, and records review, list-access, report-access, and export activity in `kk_audit_log`. Anonymous users can submit a profile and check a status through rate-limited Edge Functions; neither endpoint returns profile data. Admin RPCs require `public.is_portal_admin()` on the database.

Do not run the workbook import against production. The importer refuses to commit unless `KK_IMPORT_ENV=staging` and the configured project reference matches the Supabase URL. No import has been performed by this implementation.

## Workbook mapping and review flags

- `Email Address` and `EMAIL ACCOUNT` are retained separately; neither is selected as the canonical email.
- Legacy response IDs are not present in the workbook. The importer uses a workbook checksum and source row number for idempotent staging identity.
- Existing SK applications with a `kkProfile` are backfilled to the restricted table and marked `needs_review`.
- Legacy rows are imported as `needs_review`; source timestamps are retained as raw text when parsing is uncertain.
- Two-digit-year dates are not guessed. Date/age inconsistencies, timezone uncertainty, classification mapping, malformed fields, and possible duplicate identifiers remain review flags.
- The source timestamp timezone and the official sitio/address list are still unconfirmed. Do not normalize these during import without an approved source.

## Apply and validate in staging

1. Apply `supabase/kk_profiling_migration.sql` to a non-production staging database.
2. Deploy `submit-kk-profile` and `check-kk-registration` Edge Functions and verify their environment variables and rate-limit RPC dependencies.
3. Run the parser tests and a dry run. The workbook is read without modification and dry-run output contains aggregate quality counts only:

   ```powershell
   python scripts\test_import_kk_workbook.py
   python scripts\import_kk_workbook.py "C:\path\to\approved-workbook.xlsx"
   ```

4. Review the dry-run counts, mapping decisions, timezone, and source workbook approval. Use an authorized staging admin UUID and set `KK_IMPORT_ENV=staging`, `SUPABASE_STAGING_PROJECT_REF`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `KK_IMPORT_ACTOR_ID` in the process environment only. Never put the service key in source control or command output.
5. Only after explicit staging approval, run the same command with `--commit`:

   ```powershell
   python scripts\import_kk_workbook.py "C:\path\to\approved-workbook.xlsx" --commit
   ```

The dry run is read-only. The commit path stages rows in chunks, finalizes them idempotently, and reports aggregate counts without printing profile values.

## Review, export, and rollback

Use the admin **KK Profiling Responses** module to search by reference/name, review records, add internal notes, and set a status. Search and aggregate-report access are logged without storing the search term. Full-record CSV export requires a stated purpose and is generated by a role-checked database function; the audit event includes the actor, purpose, and exported count. Export files contain sensitive personal data and must be stored and shared only under the organization’s approved handling rules.

To roll back an imported staging batch, call `rollback_kk_import_batch` with its batch UUID using the service role. Rollback is blocked if any imported response has been edited or reviewed. The batch and audit history are retained. The source rows and raw payload are not automatically purged; retention remains subject to a records-retention policy.

## Reindexing

No external search index is used. The migration creates B-tree indexes for response status/date, source/date, age, birthday, and sitio, plus a GIN index for youth classifications. PostgreSQL maintains these indexes automatically; no manual reindex is needed during normal operation. If database maintenance requires it, use PostgreSQL `REINDEX` under the database operator’s approved maintenance procedure.

## Current limitation

The existing portal admin gate and the database `admin_users` authorization must be configured consistently. The browser hides the module behind the existing admin route, while every KK data RPC performs its own database role check. A local UI build does not validate migration execution, Edge Function deployment, or staging policies.
